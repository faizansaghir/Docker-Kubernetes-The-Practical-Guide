- **Volumes**
  - When some data that is stored inside a container needs to be persisted even when container is stopped and removed, we can use Volumes
  - <img width="720" height="406" alt="volumes" src="https://github.com/user-attachments/assets/1d3d69bb-6d38-47a7-9a2a-378083862686" />
  - We can specify that an image will use volume using `VOLUME ["vol1", "vol2"]` in the `Dockerfile` eg: `VOLUME ["/app/feedback"]`. Docker will then make sure this path mentioned is teated as external path that is mapped to some path in host machine. These are anonymous volumes. We can also create anonymous volume using `docker run -v <path-inside_container>` and without specifying it inside `Dockerfile`
  - Volumes can be listed using `docker volume ls` and anonymous volumes have name as randomly generated UUID. These get deleted as soon as we stop the container if we use `--rm` during spin up
  - In case we do not use the `--rm` flag during spin up, the anonymous volume is persisted but when we spin up a new container with same image, a new anonymous volume is created and the earlier one is not re=used
  - To remove an unused anonymous volume, use `docker volume rm <volume_name>` or to remove all unused volumes, use `docker volume prune`
  - We have another type of volume which can be persisted even when container is deleted called named volumes. These are also mapped to some location on host machine by docker without user intervention
  - Named volumes do not need definition inside `Dockerfile` like anonymous volumes
  - We can create a named volume while spinning up a container using `docker run -v <named_volume_name>:<path_inside_container>` eg: `docker run -d -p 3000:80 --rm --name feedback-app -v feedback:/app/feedback feedback-node:volumes`
  - <img width="720" height="406" alt="volumes_and_bind_mounts" src="https://github.com/user-attachments/assets/778694f3-38de-43f6-a1b6-ce5933da3cf1" />
  - A bind mount is created/ used when we want the data to persist and also be editable by us i.e. we know the location from where we can edit the shared files
  - To create a bind mount, we use `docker run -v <absolute_path>:<path_in_container>` eg: `docker run --name feedback-app -p 3000:80 --rm -d -v feedback:/app/feedback -v "C:\Users\world\Desktop\Docker-Kubernetes-The-Practical-Guide\Docker-Kubernetes-The-Practical-Guide\Module 3\data-volumes-03-adj-node-code:/app" feedback-node:volumes`. We need to make sure that docker has access to the path we are creating mount to.
  - When we create a volume or bind mount, we overwrite container filesystem with what we have present outside, so in our case, we created `node_modules` using `npm install` but then overwrote it using bind mount, thus `node_modules` folder gets deleted
  - To overcome or persist a specific path inside container without being overwritten, we can use anonymous volumes. Docker gives preference to most specific path in case we use multiple volumes eg: `docker run --name feedback-app -p 3000:80 --rm -d -v feedback:/app/feedback -v "C:\Users\world\Desktop\Docker-Kubernetes-The-Practical-Guide\Docker-Kubernetes-The-Practical-Guide\Module 3\data-volumes-03-adj-node-code:/app" -v /app/node_modules feedback-node:volumes`, here it will create an anonymous volume for `/app/node_modules` which is more specific then it will create bind mount for `/app` and anonymous volume will take preference of `/app/node_modules` folder, hence it will not be deleted. Using this, we can achieve both preserving `/app/node_modules` and also binding `/app` folder for code changes without getting issue of `node_modules` not existing i.e. missing dependencies issue.
  - Even after using bind mount, we might face issue in files such as `server.js` which is the file being run as server. Even though we change the file, the server still runs the old file. This can be solved using specific modules for that framework like `nodemon` for `npm` which can be used instead of `node` to start sever and everytime `server.js` file changes, `nodemon` detects the change and restart the server
  - There might be issues if we are using WSL in Windows for docker even with `nodemon` as it will detect for file changes in linux environment but if our file is mounted on Windows environment, it will not be able to detect such changes. Refer [windows-wsl2-file-events.pdf](https://github.com/faizansaghir/Docker-Kubernetes-The-Practical-Guide/blob/main/Module%203/windows-wsl2-file-events.pdf)
  - <img width="720" height="406" alt="differences_between_volumes_and_bind_mounts" src="https://github.com/user-attachments/assets/8f751e6c-37c2-42a1-9261-5369deec1c9f" />
  - In case we create a bind mount to which we do not want to allow writing data from within the container, we can specify read only volume there using `docker run -v <absolute_path_on_host>:<path_on_container>:ro` where `ro` -> read only. If we want some subfolder to be simple volume so that we can write data there from within container, we can create a named or an anonymous volume to the subfolder with `ro` eg: `docker run --name feedback-app -p 3000:80 --rm -d feedback:/app/feedback -v "C:\Users\world\Desktop\Docker-Kubernetes-The-Practical-Guide\Docker-Kubernetes-The-Practical-Guide\Module 3\data-volumes-03-adj-node-code:/app:ro" -v /app/temp -v /app/node_modules feedback-node:volumes`
  - Overwriting/ overriding of volumes only happen when you specify it during running docker container. If a volume has been specified in dockerfile using `VOLUME [vol1, vol2]`, it will not override the volume or bind mount which a more generic path eg: `VOLUME ["/app/node_modules"]` will not override `-v "C:\Users\world\Desktop\Docker-Kubernetes-The-Practical-Guide\Docker-Kubernetes-The-Practical-Guide\Module 3\data-volumes-03-adj-node-code:/app`
  - To create a new volume, use: `docker volume create <volume_name>` and to list volumes, use `docker volume ls` and to get details of volume, use `docker volume inspect <volume_name>`
  - While using `COPY` command, in case we want to be sure we do not copy some specific file on local to image, we can use `.dockerignore` file and mention the files or folders to be excluded. Sample [.dockerignore file](https://github.com/faizansaghir/Docker-Kubernetes-The-Practical-Guide/blob/main/Module%203/data-volumes-07-added-dockerignore/.dockerignore)
- **Environment Variables and Arguments**
  - In case we want to give some flexibility to user spinning up a container to specify something which will be used inside the container, we can use environment variable using `ENV <key> <default_value>` eg: `ENV PORT 80`. The user can then specify the port or keep it default using `docker run --env <key>=<value>` or `docker run -e <key>=<value>`. We can pass multiple environment variable using `--env` or `-e` multiple times for each key value pair. Sample [Dockerfile with environment variable](https://github.com/faizansaghir/Docker-Kubernetes-The-Practical-Guide/blob/main/Module%203/data-volumes-07-added-dockerignore/Dockerfile) decleration.
  - We can also use an environment file like `.env` with `docker run --env-file <path_to_file>` eg: `docker run --name feedback-app -p 3000:80 --env-file ./.env --rm -d -v feedback:/app/feedback -v "C:\Users\world\Desktop\Docker-Kubernetes-The-Practical-Guide\Docker-Kubernetes-The-Practical-Guide\Module 3\data-volumes-03-adj-node-code:/app:ro" -v /app/temp -v /app/node_modules feedback-node:env`. Sample [environment file](https://github.com/faizansaghir/Docker-Kubernetes-The-Practical-Guide/blob/main/Module%203/data-volumes-07-added-dockerignore/.env). To use the same defined environment variable in `EXPOSE` commands, use `EXPOSE $<key>` eg: `EXPOSE $PORT`
  - Environment variables can be used to populate and access sensitive information which will only b stored in environment files so that one cannot access them using docker image inspect `docker history <image>`. Also, one should make sure the environment file is not copied or committeed anywhere
  - Similar to environment variables, we can also have variables that can be provided during image build to use them during the image build process. These are called Build Arguments and can be defined in Dockerfile as `ARG <key>` or `ARG <key>=<default_value>` eg: `ARG DEFAULT_PORT=80`. These can then be used in any command except `CMD` as `CMD` runs during runtime while other commands run during build. Sample [Dockerfile with build argument](https://github.com/faizansaghir/Docker-Kubernetes-The-Practical-Guide/blob/main/Module%203/data-volumes-07-added-dockerignore/Dockerfile) decleration
  - To use build argument in another command, use `<COMMAND> $<ARG>` eg: `ENV PORT $DEFAULT_PORT`. We can then provide the build argument during build using `docker build --build-arg <key>=<value>` eg: `docker build -t feedback-node:arg --build-arg DEFAULT_PORT=80 .`
